---
title: 'Schema validation'
description: 'Validate and transform stored values with a synchronous Standard Schema.'
---

Persisted data can outlive the code that created it, and users or other scripts can change it. A
TypeScript type alone cannot guarantee that a stored value still has the shape your application
expects.

Schema validation checks values when you read them, helping you handle outdated or invalid data
before using it.

```ts lib/app-storage.ts
import { createStorage } from 'ultrastorage';

export const appStorage = createStorage({ prefix: 'acme' });
```

Validate with any libraries that support [Standard Schema](https://github.com/standard-schema/standard-schema), as long as validation is synchronous.

```ts app.ts
import { z } from 'zod';
import { appStorage } from './lib/app-storage';

const UserSchema = z.object({ name: z.string(), age: z.number() });

// Returns typed value if valid, null if validation fails
const user = appStorage.getItem('user', { schema: UserSchema });
```

## Read semantics

Validation happens on read, not on write. Invalid data reported as schema issues returns `null` and
remains in storage.

Successful transformations return the schema output. Async schemas throw a TypeError, and
exceptions thrown by a schema propagate.

A TypeScript generic alone does not validate the persisted value. Browser storage can change outside your application, so use a schema when runtime validation matters.

For inferred React values and defaults, see [React schemas and types](/guides/react#schemas-and-types).

:::info[Presence does not imply validity]
`has()`, `keys()`, `key()`, and `length` check whether entries are recognized and non-expired. They
do not apply your schema, so an entry can be present while a validated read returns `null`.
:::

```ts app.ts
appStorage.setItem('user', { name: 'Alice', age: 'unknown' });

appStorage.has('user'); // true
appStorage.getItem('user', { schema: UserSchema }); // null
```

Schemas are supplied per read, not registered against a key. `getOrInit()` and `updateItem()` read
without a schema; their type arguments do not validate existing values. Validate explicitly when
using these helpers with data that might have the wrong shape.

:::warning[Transformations do not migrate stored data]
A successful transformation changes the returned value without writing it back. Saving the result
requires an explicit write in a format the schema accepts on subsequent reads.
:::

```ts app.ts
const CountSchema = z.string().transform(Number);

appStorage.setItem('count', '2');
appStorage.getItem('count', { schema: CountSchema }); // 2
appStorage.getItem('count'); // '2': storage still contains the original string
```

Persisting a transformation is a separate write. Before doing so, ensure the schema accepts that
output on subsequent reads: `CountSchema` above rejects a stored number because it requires a
string input. For schema changes, explicitly migrate entries into a format the new schema accepts.

This also matters for [React setters](/guides/react#schemas-and-types), which write values using
the schema's output type.
