---
title: 'Destinations and serializers'
description: 'Choose where values are saved and how they are encoded.'
---

A destination is where ultrastorage saves values. Persistent browser data may belong in
`localStorage`, tab-specific data in `sessionStorage`, and test or server data in memory.

You may also need a particular serialization format. ultrastorage lets you configure both while
keeping the same API.

## Choose a destination

Pass `localStorage`, `sessionStorage`, or any object that implements `Storage` through the
`storage` option. Use `createMemoryStorage()` for tests and server-side rendering.

```ts
import { createStorage, createMemoryStorage } from 'ultrastorage';

const appStorage = createStorage({
  prefix: 'acme',
  storage: typeof window === 'undefined' ? createMemoryStorage() : undefined,
});
```

## Save values in memory

`createMemoryStorage()` returns an in-memory `Storage` implementation for tests or server-side
usage.

```ts
const memory = createMemoryStorage();
const appStorage = createStorage({ prefix: 'acme', storage: memory });
```

Use a separate in-memory object for each server request when saving request-specific data. Separate
instances must use the same object through the `storage` option to receive each other's local
notifications.

## Custom serialization

Don't like devalue? Bring your own `stringify`/`parse` and we won't judge. Much.

```ts
import superjson from 'superjson';

const appStorage = createStorage({
  prefix: 'acme',
  serializer: { stringify: superjson.stringify, parse: superjson.parse },
});
```

If you provide your own serializer and want to keep `devalue` out of your bundle entirely, import
from `ultrastorage/core` instead. The only difference is that `serializer` is required.

```ts
import { createStorage } from 'ultrastorage/core';
import superjson from 'superjson';

const appStorage = createStorage({
  prefix: 'acme',
  serializer: { stringify: superjson.stringify, parse: superjson.parse },
});
```

Changing serializers can make existing entries unreadable. Prefer a new prefix when changing
formats and explicitly migrate any values you need to retain.

<Callout type="info" title="Serialization limits">

The default devalue serializer supports rich data, but rejects functions, promises, symbols, and
arbitrary class instances. Serialization errors propagate from the write; see
[error handling](/reference/storage#error-handling).

</Callout>

A custom serializer must synchronously encode and decode the entire storage envelope, including
its value, marker, version, and expiration metadata. Its supported value types determine what you
can store reliably.

For example, plain JSON does not preserve `Map`, `Set`, or `Date` types, and drops object properties
whose value is `undefined`. Storing `undefined` as the entry value drops the envelope's required
`value` property:

```ts
const appStorage = createStorage({ prefix: 'acme', serializer: JSON });

appStorage.setItem('optional', undefined);
appStorage.getItem('optional'); // null: the stored envelope is not recognized
appStorage.has('optional'); // false
```

<Callout type="info" title="JSON fallback only runs after a parser error">

When decoding an entry, ultrastorage first calls the configured parser. It tries `JSON.parse()`
only if that parser throws. A parser that successfully returns an unrecognized envelope does not
trigger the JSON fallback.

</Callout>

Both paths still require a recognized storage envelope; fallback does not make raw strings or
ordinary JSON values readable. Use [explicit migration](/reference/storage#getorinit) for those
values.

Entries left in an unreadable format still occupy backend storage, and `clear()` cannot remove
them. Keep access to the old serializer while migrating, or remove known obsolete keys explicitly;
see [clearing unreadable entries](/reference/storage#clear).
